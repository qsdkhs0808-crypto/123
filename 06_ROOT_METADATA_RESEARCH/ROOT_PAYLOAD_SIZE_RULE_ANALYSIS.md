## 2. 핵심 가설 검증 및 판정

### 가설 1: 루트 declared_payload_size는 '일반 레코드의 4바이트 정렬 후 크기 합계'인가?

- **실측 검증**: 7개 RDB 전수에서 `declared_payload_size`와 `all_normal_aligned_sum`을 비교한 결과, **모든 RDB에서 완전히 불일치(NO)**합니다.
  * 예: ScreenLayout PK 루트 declared는 `2,259,136 B`, 일반 레코드 정렬합은 `1,385,508 B` (차이: +873,628 B).
- **판정**: ❌ **기각 (FAIL)**. 루트 declared는 RDB 파일 내 레코드 바이트 크기가 아닙니다.

### 가설 2: 루트 declared_payload_size는 '레코드 수 × 고정 배수(내부 캐시/구조체 크기)'인가?

- **실측 검증**: 각 RDB에서 `declared / record_count`를 계산한 결과:
  * `CharacterEditor.rdb`: PK `138.86`, CE `138.86`
  * `FieldEditor4.rdb`: PK `139.11`, CE `138.99` (delta 비율: `136.00`)
  * `KIDSSystemResource.rdb`: PK `139.18`, CE `139.06` (delta 비율: `138.30`)
  * `MaterialEditor.rdb`: PK `139.08`, CE `139.03` (delta 비율: `136.00`)
  * `RRPreview.rdb`: PK `139.05`, CE `139.02` (delta 비율: `138.00`)
  * `ScreenLayout.rdb`: PK `139.20`, CE `139.16` (delta 비율: `138.75`)
  * `system.rdb`: PK `139.16`, CE `139.16`
- **해석**: 모든 RDB에서 레코드 1개당 약 **136 ~ 140 바이트**의 매우 좁은 범위(평균 139 바이트 내외)를 일정하게 유지하고 있습니다.
  * 이는 게임 엔진(KT Koei Engine) 내부에서 RDB를 읽어 들일 때, 메모리 상에 구축하는 **내부 인덱스 해시 노드/캐시 구조체 테이블의 할당 크기**일 가능성을 강력하게 시사합니다.
  * 그러나 정확한 구조체 크기(예: 136B vs 140B vs 가변 버킷)와 동적 할당 공식은 실행파일 역공학 없이 수학적으로 단일 상수로 확정할 수 없습니다.
- **판정**: ❓ **미확정 (UNKNOWN)**. RDB 인덱스 메모리 캐시 크기 가설이 유력하나, 확정 산식 부재.

## 3. ScreenLayout 후보에서의 루트 declared 갱신 가설 평가

1. **`2,259,136 + 416 = 2,259,552` 가설 평가**:
   - `+416` 바이트는 4개 레코드의 직렬화 바이트 증가량입니다.
   - 그러나 가설 1에서 보았듯이 루트 `declared_payload_size`는 파일 내 바이트 크기가 아니라 메모리 캐시 크기 계열이므로, **직렬화 바이트 `416`을 그대로 더하는 것은 구조적 근거가 없습니다**.
   - 만약 평균 레코드당 배수($\approx 138.75$)를 적용한다면 $4 \times 138.75 = 555$ 또는 $4 \times 136 = 544$ 등이 되어야 하지만, 이 역시 추측에 불과합니다.
2. **최종 안전 권고사항**:
   - 구조적 계산 공식이 규명되지 않은 상태에서 루트 필드를 임의로 변경하면 엔진 메모리 할당 버그를 유발할 수 있습니다.
   - 따라서 포팅 시 **PK 원본 루트 레코드의 `declared_payload_size`(`2,259,136`)를 그대로 유지**할 것을 강력히 권고합니다.
